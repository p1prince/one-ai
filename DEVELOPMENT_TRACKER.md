**Current focus: Batch 5 — Plugin architecture and developer SDK.**

Batch 3 and Batch 4 implementation is in place: provider-neutral AI contracts, HTTPS adapter, shared orchestration, cancellation handling, validated disabled-by-default commands, lifecycle controls, shared main/bubble execution routing and unit tests. Initial CI validation found Kotlin compile errors; the callback and JSON array issues were corrected, but Android Validation run #162 passed on the previous branch head. The first validation of the Bubble scrolling change (#165/#166) exposed an incorrect ScrollView layout-parameter reference; this was corrected in commit `de05939` and the corrected head passed fresh Android Validation on both push run #169 and PR run #170 (compile and unit tests; no APK). Provider endpoints reject embedded credentials/fragments and redirects are disabled. The bubble command path reuses one store instance per execution. Batch 5 includes a versioned declarative plugin manifest, capability and dependency validation, dependency-aware enable/disable/remove rules, backwards-compatible manifest metadata persistence, Plugin Centre error feedback, validator tests and SDK documentation. The latest addition defines a generic trusted PluginAdapter contract and PluginRuntime registry exposed by the shared core store: registration checks installed state and manifest/capability agreement; invocations enforce enabled state, bounded input, and the central action gateway before calling adapter code; sensitive actions pause for exact-action one-time approval; cancellation is propagated and adapter failures are sanitized. Plugin disable/removal unregisters adapters and revokes outstanding approvals. Runtime contract tests cover registration, disabled plugins, low-risk execution, sensitive approval, and input limits. These are core contracts only: no feature adapters are registered yet, so Web, Screen, Voice, App, Device and Automation remain non-operational. Batch 6 now also classifies network access as sensitive, rejects malformed or oversized action descriptions, and has corrected policy tests. It remains in progress pending full integration and validation: the reusable approval dialog is not wired to a live action producer or device-action executor, and Android runtime permission flows are not implemented. Batch 7 has begun: the Bubble now filters stale saved service toggles against the currently installed and enabled plugin set, retains the independent overlay and in-bubble command path, ties command jobs/results to the foreground service lifecycle, clamps restored and dragged icon coordinates to the visible display, handles overlay-window failures without crashing the service, and constrains long Bubble panels to a scrollable viewport. Placeholder text now clearly states that Web, Screen, Voice and Automation execution paths are not implemented. Additional security tests now cover malformed and oversized action details. The initial Bubble scrolling CI failure was traced to the panel child layout-parameter type and fixed in `de05939`; corrected-head CI validation passed on push run #169 and PR run #170 (compile and unit tests; no APK). Device testing remains required. The screen-capture hand-off path is not present in the currently reviewed source and must be implemented as a separate capture-session flow that keeps selection outside the Bubble and returns results inside it; device testing remains required.

## Working rules

- Keep the Android shell usable when optional plugins are absent or disabled.
- New plugins and bubble services default to disabled.
- Do not dynamically load untrusted executable plugin code.
- Android actions require the appropriate platform API, explicit user permission and confirmation where sensitive.
- Do not claim an integration works until its end-to-end path has been implemented and tested.
- Do not run APK builds while batches 1–11 are in progress.
- Update this tracker at the end of each batch and identify the next active batch.
